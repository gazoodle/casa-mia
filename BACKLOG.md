- **Slow through Nabu Casa: cut the bandwidth** (first step done in 2026.10.3-b31: through HA the card caps its pixel ratio, `away_sharpness`, Balanced 1.5 by default; still to measure away, and the ideas below). Longer term, two ways to send only what changes: our own block updates (each stream keeps the last frame sent, sends only blocks that changed past a noise threshold, the card paints them on a canvas, a full frame now and then; big savings on quiet scenes, our own small codec), or real H.264 through go2rtc/WebRTC (HA ships go2rtc; best compression and hardware decoding, but an encoder per picture size and a `<video>` in the card). Automatic step-down on a slow link needs a signal the card lacks (an MJPEG `<img>` reports no frames in Safari; `navigator.connection` is Chrome only), so fixed levels first. Background: Away from home over Nabu Casa, with the compositor on, the whole HA UI was very slow; over a VPN to the LAN (IPv4, so the card takes the direct route) it was fast, so the path through HA and Nabu Casa is the problem, not the box. Measured 2026-10-06 with b30's figures (compositor `/status` `sending`, `pictures`, `round_s`): the device away held **two** streams at once through HA (one commander shown twice, 2208×1640 and 2208×1240 at dpr 2, 350–420 kB a frame), about **2.2 Mbit/s** together; a tablet at home took 280 kbit/s direct (1128×520). The box itself was busy but not choking: a round of about 30 stills took 1.65–2.6 s and drawing three pictures about 0.7 s, so a frame came every ~2.6 s rather than 2 s, the same at home and away; the compositor waited 0% to send (HA's proxy reads at LAN speed, so any wait is between HA and the viewer, logged by `pictures.py` at each stream's end: not yet seen). Suspects: the bytes (dpr 2 is four times the pixels of dpr 1), and HTTP/1.1's six connections per site (Nabu Casa passes the browser straight to HA's aiohttp, so each held stream takes one from the UI's own requests). Ideas: through HA, ask for dpr 1 (or a lower cap, or a lower JPEG quality) for about a quarter of the bytes; one stream per device through HA (end the older one rather than MAX_STREAMS = 3); a slower frame rate away; poll single frames (`.jpg`) instead of a held stream, which frees the connection between frames. First get the HA log's "picture … ended" lines (kbit/s, % waiting) from a session away (they are INFO, which HA hides by default: set the integration's log level to info first, e.g. `logger: logs: custom_components.casa_mia: info`), and compare UI responsiveness with each idea. Separately, the round could be shorter: small panel tiles need not be fetched every 2 s.

- **FONA tests: stop them being flaky on CI** (asked 2026-10-10). `tests/test_fona.py` keeps failing on GitHub's runners and passing locally, blocking releases (the latest: the 2026.10.7 release pull request, `test_ping_is_answered_for_anyone_then_checked` checking for the PONG reply straight after waiting for the text's event; fixed in that test only). Find a reliable way: wait for each thing a test asserts (or have the fake record with an event to wait on), audit every test in the file for check-after-other-wait, consider driving the module's read and write loops in-thread with a controlled clock instead of real threads, and prove it by running the file many times under CI-like load (`pytest -n 8 --count`, or a loop, with the CPU busy). The whole suite must stay under 15 s.

- **FONA Arduino firmware into the repo** (later; it works and needs no attention now). The sketch is `FonaForHA` (`FonaForHA.ino`, a FONA class, `InputBuffer.cpp/.h`, about 1,000 lines) on the Adafruit FONA library. It speaks the line protocol the `fona` module reads (`RING:`, `TEXT:`, `RSSI:`, `INFO: FONA <v> start|ready`, `OK`/`FAILED`; commands `START`, `ERASEALL`, `RSSI`, `SEND:`, `RESET`) and is the first PING layer ("PONG from Arduino", sent to any number before any allowlist check). Bring it in with a build (arduino-cli) and a build plan for the board, so others can make the same; this is now part of the public release. Changes worth making then (found while writing the app's `fona` module):
  - **Texts can be lost.** The sketch deletes each SMS from the SIM straight after printing it, with no acknowledgement, so a text that arrives while the app is restarting or the port is closed is gone. And `ERASEALL` on every start (asked for by the host, kept from the old integration) wipes anything still stored. Better: the host acknowledges each text (`ACK:<slot>`) before it is deleted, and on start the sketch reports stored texts instead of erasing them; then drop the host's `ERASEALL`.
  - **Replies don't match commands.** Only `SEND` and `ERASEALL` answer `OK`/`FAILED`; `START` answers `INFO ... ready` or `ERROR: FONA not found`, `RSSI` its own line, `RESET` and `AT...` nothing. One reply per command (or tagged replies) would let the host match them instead of special-casing each.
  - **Modem not found stays not found** until the host sends `START` again (the app retries every minute); the sketch could retry, or power-cycle the modem, itself.
  - **`RESET` jumps to address 0**, which does not reset the hardware; a watchdog reset does.
  - **Escaping:** new lines in texts go over serial as backslash-n, so a text that really contains a backslash followed by n arrives changed. Escape the backslash too.
  - **Long texts:** the read buffer is 250 characters and multi-part texts are not joined.
  - **Heartbeat:** the app probes a quiet line with `ALIVE?`; a periodic unsolicited line from the sketch would do the same with less traffic.

- **FONA voice calls into the voice assistant** (big, fun): instead of hanging up, answer an authorised call and connect the audio to HA's voice assistant (Assist pipeline: speech to text, a conversation agent, text to speech), so you can phone the house and talk to it; and let the house make calls (ring someone and speak a message, e.g. an alarm). Tick the ones you want; each becomes a group, previewed. 3. One-offs: a short list of single sensors worth a watch (a freezer, a boiler pressure), by device class. 4. Telling you: make the Notify on Sensor Watch automation (your phone from a dropdown, a level), and add the card to a dashboard. 5. Done: what was made, with a way back to each. Everything it makes is the ordinary groups, profiles and watches, editable as usual afterwards.

- **No watching itself: loops, jams and hysteresis hell** (asked 2026-10-11). Sensor Watch's own entities (status, counts, problem) are already left out of every list it offers (`history.py` skips platform `casa_mia_sensor_watch`), so the watch dialog, scans and groups can't pick them. Still open:
  - **The API takes them anyway:** a `PUT` for `sensor.casa_mia_sensor_watch_status` (by hand, or an import) would be saved. Refuse the integration's own entities in `clean()` or `_record()`, with a message that says why.
  - **The indirect loop:** a template helper that reads Sensor Watch's entities or attributes (a "worst level" template, a count), then watched; or an automation on the event that changes a watched entity (turns a light on, which a watch then flags). Each change of level can feed the next. Hold-offs damp it but needn't stop it, and an inverted mapping oscillates for ever. Ideas: warn in the watch dialog when a template helper's own template mentions `casa_mia_sensor_watch` or its entity ids (HA's template config entries hold the template); a circuit breaker in the integration (the same entity changing level more than N times in M minutes is held at its worst level, logged, and says "flapping" as its message); a line in the guide's "What it won't do".

Climate needs it most: its state is a mode (heat, off, auto), which says nothing about health; the signals are a room far from its target, or heating for hours without getting there (today: a template helper for the difference, see Watch a template).
- **The target, in the owner's words** (2026-10-11): pattern-match your major classes of stuff with auto-groups (every Shelly, every leak sensor, every battery, every Hue light, every window), which ensures they're set up and stay done; check your bands; add the one-offs as single watches (the freezer, the softener's salt, the alarm number); the rule of thumb: **more than two of the same kind is a group, a single thing is a watch**. Then one automation: when the status or the problem sensor flips, "something needs looking at". All in half an hour, and you have plant-level monitoring and signalling. When groups and profiles ship, this becomes the guide's opening, the README's pitch for Sensor Watch, and the community post's hook; not before (it isn't true until then).
- **Sensor groups that keep themselves up to date** (built in b15–b21: filters with minus words, a profile or the defaults, a live preview, new arrivals joining as HA adds them, left-out remembered, the `list` service by group; still open below: suggest-from-history members, availability-only groups; asked 2026-10-11; the umbrella over band profiles, the list service by group, and availability rules below). The usual failure: set it up once, then put in a new Shelly plug and forget to watch it. A group is a **saved scan**: the filters the user scanned with (integration, device class, area, label, device, kind, search) plus what to apply to whatever matches: a **band profile**, the **device-class default**, or **suggest from history** (a new member waits for a few days of it, shown as pending). In the scan's results, **Create auto-group** beside Watch the ticked; everything matching joins now, and **new arrivals join by themselves** (the app re-reads HA's entities each minute anyway), logged and fired as an event ("joined Mains voltage") so it can be told. **Leaving is remembered**: Stop watching a member and the group won't pull it back. The group is a filter everywhere: a chip on the watched list, the `list` service's group filter (so a panel asks for its group). An **availability-only** group (every Hue light, counted per device, levelled by how many and how long) may be Availability rules with a different rule: design them together.
- **Band profiles** (built in b11–b13: profiles, followers, New/Edit/Apply to…; device-class defaults as built-in profiles still open) (asked 2026-10-11): say a range once for many sensors. A scan suggests bands per sensor from its own history, so twenty Shelly plugs get twenty slightly different sets, and making them all one standard (UK mains: critical below 207 V, a warning below 216 V, nominal to 253 V) means editing twenty records: un-DRY in our own house. A profile is a named set of bands (or exact states) that records point at; edit it once and every sensor on it follows. A scan offers "use a profile for all ticked"; the editor shows which profile a sensor follows, and lets one sensor leave it. Device-class defaults could become built-in profiles.
- **The list service and summaries by group** (asked 2026-10-11): `list` (and perhaps the status sensor's lists) filters by level only, so a panel for "just the Shelly plugs" filters entity ids in its template. Let `list` take a label, area, integration or device too, so a panel asks for exactly what it shows.
- **Notify on Sensor Watch, the blueprint** (built in 2026.10.8-b25; asked 2026-10-11): installed by the integration into `blueprints/automation/casa_mia/`; level or worse, a group, a notify action, a persistent notification per sensor cleared when back, recovery, further actions. Groups and notify actions are dropdowns, written into the file by the integration (b26). Still open: the notify entities of HA's newer `notify.send_message` once the mobile app has them.

- **Availability rules** (the simple half built in 2026.10.8-b24: an **Available** mode, per entity, either way round, with groups for "every Hue light"; still open: counting per device and one row per rule, below; asked 2026-10-11): watching only "is it there?" for many things at once, without a record each (a Hue bulb has nothing else to go wrong; a global "anything unavailable" is mad). Thinking so far:
  - **Rules, not records:** a rule picks things by integration, device, area, label or domain ("every Hue light", "everything labelled Essential") and watches availability only; new devices join it as the registries change.
  - **Per device, not per entity:** a bulb is a light and a few sensors that drop together; count the device once.
  - **One row per rule, levelled by how many:** "Hue lights: 2 of 38 unavailable", a level by count or share (one a task, over 10% a warning). All of them at once is usually the bridge or the integration, which the failing-integrations check already reports.
  - **Time, not the moment:** bulbs switched off at the wall are unavailable in normal use, so a long hold-off (an hour, a day), and a level that grows with time (a task after a day, a warning after a week).
  - **Exclusions:** Ignore per device (the lamp on a wall switch), and a label (e.g. "Sensor Watch: ignore") every rule respects, settable from HA's own UI.
  - Cost: HA's one state tracker takes thousands of entities cheaply, as now. Close to Stale sensors (gone quiet but still "available"): perhaps one feature.
- **Escalation** (asked 2026-10-12; the algorithm is the owner's, to come): a level that has stood for a further while moves up to the next severity, for every kind of watch and every level, nominal included (a task left for a week becomes a warning; a sensor nominal for too long may itself be a sign, a value that should move). Wait for the owner's algorithm before designing: per level or per watch, how long at each step, where it stops, whether recovery resets it, and how the event and the page say it escalated rather than changed.
- **Stale sensors** (asked 2026-10-11): "no change for N hours" as a level, for battery devices (Zigbee and the like) that stop reporting but still show available, and for any sensor that should move (a temperature that hasn't changed all day). Per record, off by default; perhaps a scan default by device class.
- **Watch a template** (asked 2026-10-11): some faults only show between sensors, e.g. power meters on the same wire all report voltage, and a downstream meter that differs from the upstream one may be a critical fault. A **+ From a template** choice in the Watch dialog: type a template (a value, such as the voltage difference, or true/false) and a name; Casa Mia creates it as an HA template helper through the "Entities Casa Mia makes" module below, and opens the bands editor on it. A real entity, so it has history (suggestions, the chart, scans), and HA renders it only when what it reads changes.
- **Dependencies** (asked 2026-10-11): a record can name an upstream sensor and count only while that one is nominal, so a real supply drop raises one alert, not one per downstream meter (which would swamp the UI). Think it through first: chains, what the summary shows for a suppressed sensor, and loops.
- The owner's own ESPHome devices come from a generator that knows each meter's upstream link, so it could produce the difference sensors (and the dependencies) itself; Sensor Watch should take them as they come, not assume it made them.
- **Richer matching, after auto-entities' filter language** (floor, maker, model and category built in 2026.10.8-b23; asked 2026-10-11; Thomas Lovén's card, MIT: borrow the ideas, not the code, and don't depend on it). Groups and searches match today on domain, area, label, integration, device, device class, kind and words (with `-word` to rule out). His include/exclude rules also take: **floor**, **device manufacturer** and **device model** ("every Shelly Plus Plug S", not "every voltage"), **entity category** (diagnostic entities, where an ESP board's VCC reading usually lives), **attributes** (`unit_of_measurement: V`), **state compared** (`"> 100"`, which tells mains from a 3.3 V rail whatever they're called), **last changed / updated ago** (`"> 1h ago"`: close to Stale sensors), **hidden by**, and **name / entity_id** with `*` wildcards and `/regex/`; combined with **not**, **or** and **and**, and the same option repeated. Pick what earns its place in a point-and-click page (floor, manufacturer, model and entity category first; then attributes and a state range), keep the one-line chips, and keep the app's `matches()` and the page's `searched()` agreeing (a test). Floors also suit the per-floor room temperature profiles (Duplicate…).
- **"Watch in Sensor Watch…" from HA's own entity dialog** (asked 2026-10-11). The cheap version: `cm-cards.js` (on every HA page) notices the more-info dialog opening and adds an item to its ⋮ menu, admins only, that goes to Casa Mia's Sensor Watch page with that entity's editor open (a deep link, `#/sensor-watch?watch=<entity_id>`, which the page honours). The dialog's insides aren't public API, so it can break on an HA release, as the Tablet Layout's patches can: keep it in one place (`ha.ts`) and fail quietly (no item, a console line). Until then the guide's tip covers it: a group filtered by a label, and the label given in HA's own entity settings. The full version is the next item.
- **Event-driven everywhere, the rest** (asked 2026-10-11; b21 made a change of level show at once: the card and the app hear the integration's event, the entities write at once then coalesce, groups hear HA's registry). What still waits on a clock or a second-hand signal, and what to do. How the records and levels move between the app and the integration is in "Sensor Watch's records: pushed, then owned by the integration" (above); this item is what that leaves:
  - **Home Assistant's own health** (`system.py`) checks every minute. Trigger it on config-entry changes instead (HA's `config_entries/subscribe`, or its dispatcher inside the integration), keeping a timer only for the five minutes an integration must fail for before it counts.
  - **The candidates cache** (`history.Reader`, 60 s): drop the time limit and forget it when HA's entity, device, area or label registry changes (the live feed already hears the entity registry), so the pages always see now and never re-read for nothing.
  - **`list` calls open a fresh websocket each time** (`HA.call`: sign-in through the Supervisor per call). Step one (b13) removed the `list` after every write, and the Home tile's health now comes from the integration's own entities. The `list`s left (at connect, after every record is pushed, and after the integration fetches them itself) could go over the live feed's own connection.
  - **The card asks the whole `list` on each event**: in a big house, apply the event's row to what it has (as the live feed does), asking the whole list only now and then.

- **Export to native Home Assistant** (asked 2026-10-11): "I don't want your crud sullying my lovely clean HA system", and the honest exit for anyone leaving. Write the chosen watches out as plain HA: each profile a Jinja macro in `custom_templates/`, each watched sensor a template sensor giving its level (importing its profile's macro), hold-offs as `for:` / `delay_on`, a summary template over a label, the event as an automation, the `list` service as a script with `response_variable`. The user reviews it, drops it into a package, and can then remove Casa Mia (see "take it all out"). What doesn't export, said plainly on the page: suggestions from history and the scan (templates can't read the recorder), HA's own health (no template lists config entries or loaded components), and scale (a level entity per sensor, and templates iterating every state re-render at most once a minute). A one-way export, not a round trip: Casa Mia never reads the YAML back.

## The app and integration as a whole

- **The release image: libraries in a layer of their own** (asked 2026-10-20). `app/Dockerfile` (the box's own build) installs PyAV in a layer before the source, so it's kept between versions; `app/Dockerfile.release` (the GHCR images everyone else gets) copies `app/src` and then runs one `pip install /src`, so every release puts PyAV (about 34 MB), Pillow, aiohttp and the rest in a fresh layer, and every user downloads them all again at each update. Install the dependencies first (from `pyproject.toml`, without the source), then copy the source and install it with `--no-deps`; a typical update then fetches a few MB. Check the layer sizes in `release.yml`'s build. Touches `app/`: bump first.
  - **Decided against (2026-10-20): downloading a module's code when it is switched on.** The module code is under 1 MB (820 KB for all of `modules/`, 1.1 MB for the admin UI, about 1.3 MB for the three components); the weight is the base image, Python and PyAV. Fetching at run time fights the image model (the image is the version: update, rollback and backups assume it holds what runs), lands in `/data` (backed up), needs the internet to switch a module on (FONA's parts must stay in the image), and a run-time `pip install` is a supply-chain fetch on the live box that can fail per architecture. A second app for the cameras would avoid that but costs a container and an API. Not worth it for 34 MB. Nor does it serve the real goal (see "Modules as stand-alone projects"): whatever is downloaded, people still install the whole Casa Mia app.

- **Push only the components whose module is on** (asked 2026-10-20). The app copies all three components into `/config/custom_components` on start, and HA logs a custom-integration warning for each. Push `casa_mia_guest_login` and `casa_mia_commander` only while their module is on. This saves clutter, not bytes. The catch: removing a folder while its config entry exists leaves HA saying "integration not found", so a component goes only once its entry is removed (as `components.py` `RETIRED` does for a retired one), and comes back before its module is offered under Discovered. Low priority: only if the start-up warnings bother people.

- **Install from any GitHub repository, private ones too** (asked 2026-10-11; needs design refinement). Installing things into HA that aren't in an App store or HACS is a pain, so help: give Casa Mia other GitHub repository addresses, and it downloads them, keeps them up to date, and (where it can) installs them: an app, an integration, a card, or whatever else. Especially useful for **private repositories**, so anyone can build a simple app or integration of their own and run it in HA with automatic updates.
  - **Build on what's here:** the firmware server (`gitproxy`) already mirrors GitHub releases, and `tools/fake_git_host.py` already serves a checkout as an App store repository. A repository could be a local folder (served as the fake git host does) or a GitHub repository, private ones reached with a GitHub token (stored as a secret, never logged).
  - **An install helper** for each kind, usable by a person or an AI agent: a script or checklist that does the steps (add the repository, install, restart, set up), as far as HA lets it.
  - **Look first at Nathan Curtis's zenos project**, for how it tackles installing; and at GoG, which may want its own version of this (the owner may decide this one is good enough for it).
  - **Open:** which kinds are worth doing first (apps through an App store repository served by Casa Mia; integrations into `/config/custom_components`, as Casa Mia does its own; cards as Lovelace resources); how updates are offered (HA's update entities, so they show in Settings → Updates); pinned versions or the latest; checking downloads; and HACS (don't fight it where it already does the job).

- **All Casa Mia config in git, optionally pushed to a private repository** (asked 2026-10-11). Every module's config (Sensor Watch's records and profiles, the layouts, guest login, kiosks, people, settings: the JSON in `/data`) kept in a git repository on the box, each change a commit (what the admin page or integration changed, as the log already says). Optionally pushed to a private GitHub repository, reusing the token and repository handling from "Install from any GitHub repository" above. The point: **hand-edit the JSON on GitHub, commit, have the box pull and regenerate**, and **stand up a brand-new HA from it**. Not a backup (HA's backups do that): a clean, deterministic rebuild, leaving behind ten years of crud and entity names that came along for the ride.
  - **Needs:** the "generated and owned" rule below (so regenerating is safe); config written in a stable order (sorted keys, no timestamps in what's compared) so diffs show only real changes; secrets kept out of the repository (tokens, guest slugs, passwords stay in `/data` only, referenced by name); a pull that checks the JSON (each module's own `clean()`) before taking it, and says what it refused.
  - **Open:** entity ids in the config point at the old house's names; a fresh HA has new ones. A rename map (old id to new), applied on import, may be the tool that does the tidying: the moment to fix the nasty names, once, in one place. Also: which way wins when the box and the repository both changed (probably the repository, with the box's changes kept on a branch), and how often it pulls (on request, or a webhook).

- **Generated means owned** (agreed 2026-10-11, across modules). Everything Casa Mia writes into HA (dashboards, helpers, exported packages, Lovelace resources) carries a marker ("made by Casa Mia: edits here are overwritten") and is regenerated whole, never merged. An edit made in HA's own UI is drift: reported on the page (what changed, where), then overwritten or kept by the user's choice. Same input, same bytes (no timestamps or random ids in the output), so regenerating changes nothing and "did anything change?" is a byte compare. The owner's aim: drop the hand-edited dashboard and Lovelace path altogether, for deterministic creation from sources.

- **Casa Mia's own dialogs in Home Assistant's pages** (asked 2026-10-11). Code running in HA's page (`cm-cards.js`) can open dialogs of ours over HA itself, edit mode or not: fire HA's `show-dialog` event naming our element (HA's dialog manager gives it the backdrop, focus and Esc; browser_mod does this), built from HA's own dialog and form pieces so it looks native. Talking to the app goes through the integration: websocket commands (admin only) that pass the request on as the admin page's API does, so the data and its checks stay in the app. First use: "Watch this" from an entity (the item above, without leaving the page: pick a profile, or set bands, there and then). Then wherever it helps: kiosk actions on a tablet's device page, a guest endpoint from a user's page, a garnish heading picked in the card editor. Neither `show-dialog` nor the more-info dialog's insides is public API: check them each HA release, alongside the Tablet Layout's patches (a test page per HA version, if the checks grow).

- **Bugfest** (asked 2026-10-10). A session given over to finding bugs on the box before more features or more telling people about it. Start with: do the commanders redraw after an app reload (2026.10.6 starts a fresh stream after an app restart; it may only have been triggered by an HA restart), and the handover's "untested on the box" list (2FA against a real user, the reach check's fixes, Who's signed in).

- **Swap for the live house** (asked 2026-10-10; perhaps only in developer mode). Grows from the screenshot swap (`swap.json`, which today changes only Casa Mia's own pages and pictures). Sets of replacement strings, one set per scenario, applied across HA's own pages too (a browser-level text swap, as the "cloud-to-butt" extension does), and later pictures and camera streams swapped for stand-in pictures. Why: a real, fully working HA is a better test bed than any simulator, and setting a simulator up is the painful part; the swap takes the personal data out instead, for screenshots, demos and debugging. No browser dialogs, drop-downs or checkboxes (our confirmBox/askBox, Select, and styles.css drawing checkboxes as switches); one look for all the chrome (`docs/design/chrome.html`); `tests/test_no_browser_controls.py` keeps them out.

## Guest login module (taking over `cnorick/ha-auto-guest-login`): complete, app 0.1.26

Kept as the design record; current behaviour is in the code and README.

Decision: it is part of this app's experience, so it goes in **our own app** as a Python module, not a separate app and not Node. Source read (MIT, Nathan Orick 2021, unmaintained since 2025-02, ~400 lines of Node/Express): `server.js`, `auth-client.js`, `ha-client.js`, `utils.js`, two EJS pages, DOCS.md.

What it does: a guest visits `http://<ha-host>:8675/`, the app logs the guest account in through HA's `/auth/login_flow` API, redirects the browser to a guest dashboard already authenticated, and fires the event `ha_auto_login_guest_logged_in` (data: `ip`). `/admin` (via ingress) shows the URL and a QR code. `?d=` / `?dashboard=` overrides the dashboard (done client-side in the welcome page).

**UI: rewrite, not port.** The upstream pages are clunky (fixed-size layout, rainbow-cycling title, a bare admin page). Proposals to refine when this starts: mobile-first welcome page in the app's look (guests are on phones), clear states for redirecting / failed login / HA unreachable, and an admin page with the link, a QR code and a printable QR card. Needs a design pass, so ask before building.

**Background (already in place and working, do not redesign):** guests get two QR codes. One joins the guest Wi-Fi; the other logs into HA and lands them on a locked-down dashboard at an unguessable URL. The rewrite only needs to keep that experience working with a nicer UI.

**Design (agreed; since built).** Two parts: an app module and a thin integration. The module name `guest-login` is final.

- **Endpoints, not one login.** Each QR code points at one endpoint, `http://<host>:8675/e/<slug>`: a label (a guest suite, a KNX panel), an unguessable random slug, an account, a landing dashboard, a type (guest page, or minimal engineer page) and an enabled flag. At least four guest suites, and QR codes for KNX panels and similar so visiting engineers can do maintenance and control by scanning. **The existing QR codes are immutable and must keep working exactly as they are**, so the legacy URL shapes (`/`, `?d=`) must be preserved alongside the new `/e/<slug>` ones. 
- **Existing codes (decoded from the printed QR cards):** all of the form `http://<box IP>:8675/?d=/guest-dashboards/<16 uppercase hex>`: the box's IP, port 8675, path `/`, and one random view path per suite inside a single `guest-dashboards` dashboard. One shared login today. Each becomes an endpoint carrying its `d` value as identity, so `/` with `?d=` resolves to it. The hex ids are the secret part; they are not recorded here. Behaviour changes, confirmed: an unknown `d` is refused (upstream redirected anywhere), and every endpoint starts off, so each must be switched on once (or by an automation) before the old guest login is retired (test one suite first). Printed cards need no reprint while the URL is unchanged.
- **Accounts per endpoint:** v1 points all legacy endpoints at the one default account (as today), but the model is one account per endpoint, so a suite can later move to its own HA user by changing the endpoint's account name; QR codes are unaffected. Separate users enable revoke-on-disable (switching an endpoint off also revokes that user's refresh tokens, logging out a guest already inside; impossible with a shared user, it would kick every suite), per-suite dashboard views via user conditions, and per-user logbook entries. HA has no per-user entity permissions, so this is not a hard lock-down.
- **Gating is the point.** Every endpoint is **off by default**; an automation (or you) turns it on, and the state is **remembered across app and HA restarts** (changed from the first design, which reset it on every restart and closed every suite on each update; saved in the app's data folder) (booking system, alarm state, a timed window). A disabled endpoint refuses the login with a plain "not available" page that gives nothing away. The unguessable URL and the switch are not a security boundary once someone is logged in, because an HA user is not confined to one dashboard; engineer accounts must be **non-admin** with a minimal dashboard. No PIN.
- **Accounts:** a default account plus extra named ones that endpoints refer to, in app options (passwords). The endpoint list (id, label, dashboard, type, account, slug, legacy) is the `guest_endpoints` app option too (decided: the legacy ids and slugs are secrets and stay out of git; the app options are validated by the schema and backed up with the app).
- **Guest pages:** welcome and login (signing in, success, failed, HA unreachable; mobile-first, the app's look), plus a house-info page (Wi-Fi, house rules; may be dropped later). Admin page (ingress): endpoints with their state, a QR per endpoint, a printable card, recent logins.
- **Integration:** a "Guest login" device with a child device per endpoint (found from the app's `/health`, so new endpoints appear on their own): an enable switch, last login, login count, and an event entity carrying the guest IP, for automations. Optional time limit on the switch. Not the legacy `ha_auto_login_guest_logged_in` event: nothing used it, the event entity replaces it.

Port notes and traps found:
- **Licence:** we are rewriting from scratch with a much nicer UI, using his code only as a description of the HA login flow. If none of his code or markup is carried over, no licence file or credit is needed. If a close port of any part survives, keep his MIT copyright and permission notice (`third_party/ha-auto-guest-login/LICENSE.md`). Use our own icon, not his logo (which is rawpixel's).
- **Environment:** the app's process does not get `SUPERVISOR_TOKEN` or image `ENV` under s6 (see the CM_COMPONENTS fix). Upstream used `#!/usr/bin/with-contenv bashio`. We need a `run.sh` with `#!/usr/bin/with-contenv bash` then `exec python3 -m casa_mia`.
- **Manifest:** `hassio_api: true`, `homeassistant_api: true`, `ports: 8675/tcp: 8675`, optional `guest_*` / `welcome_*` / `advanced_*` options (module disabled when username or password is empty, so the app still starts without them), ingress for `/admin`. Upstream's `armhf/armv7/i386`, `codenotary`, `image:` and `build.yaml` are all obsolete.
- **Supervisor calls:** HA port from `http://supervisor/core/info` (`data.port`), published guest port from `http://supervisor/addons/self/info` (`data.network['8675/tcp']`), event via `http://supervisor/core/api/events/<name>`.
- **Bug to fix in the port:** upstream builds the login JSON by string interpolation, so a password containing a quote breaks it. Use `json.dumps`.
- **Behaviour to keep:** the internal HA URL defaults to the request's hostname plus HA's port (override `advanced_internal_base_ha_url_and_port`). `homeassistant.local` can fail to resolve inside a container (mDNS); consider `http://homeassistant:8123` as the default, but test on the box first since this is an access path.
- **Code shape:** needs a small route registry in `server.py`, the draft module contract (`start()`, `stop()`, `health()`) with one module failing never stopping the others, and a second HTTP server on the guest port. QR: `segno` (pure Python, SVG) is the likely dependency.
- **Cut-over:** guest options are stored per app slug, so re-enter them once. Remove the `cnorick/ha-auto-guest-login` repository from the App store when ours works, which also removes its error.
- **Rule Zero applies:** bump the version first, add the changelog entry.
